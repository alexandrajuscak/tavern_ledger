# Migrations

Supabase CLI format (`<timestamp>_name.sql`), applied once each and recorded in `supabase_migrations.schema_migrations`.

| Version | Contents |
|---|---|
| `20261015000000_base_schema` | generated copy of `supabase/schema.sql` (do not edit: `python scripts/db/sync_base_migration.py`) |
| `…0100` – `…1100` | item catalog, inventories, equipment, RPCs, views, RLS, indexes, legacy migration function |
| `…1200` | frontend RPCs: exact quantity, move into a container, link a legacy row |
| `…1300` | homebrew items (create / update / archive / restore RPCs, visibility, audit), legacy link preview and convert, JSON import RPC; client writes to `inventory_items` / `items` revoked; homebrew author FK `on delete restrict` |

Deployment order on a remote project: all migrations in timestamp order (`supabase db push` on the linked project),
then the seed once (`psql -f supabase/seed/reference_data.sql`; re-runnable), then — only on a project with old
characters — `select public.migrate_legacy_inventory();`.
A **new empty** project applies `…0000` normally. A project that already has the base schema (production) must
instead record `…0000` as applied without running it (`supabase migration repair --status applied 20261015000000`)
after checking that its schema matches `supabase/schema.sql`; that step is for the production rollout, not staging.
A profile that still owns homebrew items cannot be deleted (FK `restrict`): delete or transfer its items first.

The reference data is **not** a migration: `supabase/seed/reference_data.sql` (generated, re-runnable), loaded by
`supabase db reset` via `[db.seed]` in `supabase/config.toml`. On a project with existing characters run
`select public.migrate_legacy_inventory();` after the seed.

Class catalog migrations (`20261017*`, generic class engine extensions; rollbacks in `supabase/rollback/`, newest first):
`000100` class engine extensions, `000200` class page read model, `000300` spellcasting class extensions, `000400` spells UX,
`000500` hybrid casters (auras, expanded lists, Pact recovery), `000600` class setup flow (Add Class preview, starting
equipment), `000700` martial engine (active states such as Rage, feature save DCs), `000800` creatures, transformations
(Wild Shape) and companions, `000900` infusions on inventory items and the class-raised attunement limit, `001000` rest
result fix (what a rest restored is reported correctly), `001100` proficiency resolver (`get_character_proficiencies`),
`001200` versioned backgrounds (2024 and legacy versions, ability increases, grants, feat references, equipment). Their
content comes from `supabase/seed/class_features.sql`, `supabase/seed/creatures.sql` (SRD 5.1, CC-BY-4.0) and
`supabase/seed/backgrounds.sql` (docs/BACKGROUNDS.md). `001300` is the Wild Shape gameplay engine: creature mechanics
status, form HP with temp HP, carry-over, duration and expiry, equipment modes, seen forms, favorites, settings, history, the
transformed sheet layered on the derived stats, Combat Wild Shape, and Realtime on `character_transformations`
(docs/TRANSFORMATION_ENGINE.md; rollback `rollback_wild_shape_engine.sql`).

Docs: [`docs/INVENTORY_DATABASE.md`](../../docs/INVENTORY_DATABASE.md), [`docs/MIGRATION_REVIEW.md`](../../docs/MIGRATION_REVIEW.md).
Local tests: `bash supabase/tests/run_local.sh` (plain PostgreSQL) and `bash supabase/tests/run_supabase_local.sh` (local Supabase stack).
Nothing in this folder has been applied to a remote Supabase project.

DM governance and content migrations (`20261019*`, rollbacks in `supabase/rollback/`, newest first:
`rollback_feat_backfill`, `rollback_derived_stats_performance`, `rollback_dm_read_models`, `rollback_hidden_dm_data`, `rollback_dm_content`,
`rollback_feat_catalog`, `rollback_change_requests`, `rollback_campaign_governance`): `000100` campaign governance (presets,
per-action decisions, locks, initial setup, gate in 75 RPCs, direct-write triggers, audit; existing campaigns become
"relaxed"), `000200` change requests (approval workflow through registered domain RPCs, preview, stale detection, atomic
apply), `000300` versioned feat catalog and feat engine (renames the background-era `feats` table to `feat_versions`;
seed `supabase/seed/feats.sql` loaded after `lineages.sql` and before `backgrounds.sql`), `000400` DM content (registry,
versions, validation, publish into the catalogs, assignment, archive), `000500` hidden DM data, `000600` DM read models,
`000700` derived-stats performance (`_character_mods`), `000800` feat backfill (materializes the resources and spells of
feats that characters already had before the feat engine, e.g. Lucky from a 2024 Wayfarer background). `000100`, `000300` and `000400` are generated by builders kept with
the local backups (they read live function definitions; see docs/DM_GOVERNANCE.md) — do not hand-edit them.
`rollback_dm_content.sql` refuses to run while custom content is in use by characters.
