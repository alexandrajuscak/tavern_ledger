# Feat data model

Migration `20261019000300_feat_catalog.sql` (generated by `build_feats.py` from `feat_static.sql` plus exact rewrites of
live functions; rollback `supabase/rollback/rollback_feat_catalog.sql`). Seed `supabase/seed/feats.sql` (generated, see
[FEAT_COVERAGE.md](FEAT_COVERAGE.md)). Behaviour: [FEATS.md](FEATS.md).

## Catalog

```
feats (canonical: "alert", "tough", campaign custom "cc-…")
  └─ feat_versions ("alert-2014", "alert-2024": one ruleset and source each, never merged)
       ├─ feat_prerequisites   (version_id, seq, grp, kind, target, value, label)   rows of one grp = OR, groups = AND
       ├─ feat_choices         (id = <version>:<key>, kind, label, min_picks, max_picks, config, parent_choice_key / parent_option_id)
       │    └─ feat_choice_options (choice_id, option_id, label, summary, data)
       ├─ feat_effects         (seq, effect_type, target, value, value_text, choice_key, option_choice_key / option_id, activation, automation, conditions, data, label)
       ├─ feat_spell_grants    (spell_version_id or choice_key, mode known / innate / always_prepared, ability or ability_choice_key, uses at_will / long_rest_1 / pb_long_rest, uses_slots)
       ├─ feat_resource_grants (key, name, max_formula, recharge)
       └─ feat_attack_grants   (key, data)
```

The table `public.feats` of `20261017001200` (backgrounds) held version rows; it was **renamed to `feat_versions`** with
unchanged ids, so background Origin-feat links (`background_feat_grants.feat_id`) kept working, and a new canonical
`feats` table was created. `generate_background_seed.py` emits a schema-aware block that works before and after the rename.

`feat_versions` columns: `id`, `feat_id`, `name`, `category` (origin, general, fighting_style, epic_boon, other), `ruleset`
(2014, 2024, ua-2022), `status` (official, playtest, third_party, unverified, homebrew), `summary`, `benefits`,
`source_label`, `source_url`, `source_book_id`, `setting`, `legacy`, `automation` (automated, partially_automated,
informational), `implementation_note`, `parameter_label`, `min_level`, `repeatable` (once, repeatable,
repeatable_distinct), `max_count`, `distinct_choice_key`, `prerequisite_text`, `tags`, `replacement_version_id`,
`owner_id` / `campaign_id` / `content_version_id` (campaign custom feats), `archived_at`, `sort_order`.

Prerequisite kinds: character_level, class_level, class, subclass, ability, armor_proficiency, weapon_proficiency,
skill_proficiency, spellcasting, pact_magic, known_spell, feat, background, lineage, size, feature, campaign_permission,
text. Choice kinds: ability_increase, asi_points, ability, skill, expertise, tool, skill_or_tool, language,
spellcasting_ability, spell_list, spell, damage_type, weapon, option, free_text.

Only the seed and the DM content materializer write the catalog; RLS lets everyone read official rows and campaign
members read their campaign's custom rows (`can_view_owned`).

## Character data

| Table | Holds |
|---|---|
| `character_feats` | direct grants: `feat_version_id`, `source_type` (direct, dm_grant, campaign_reward, approved_request, import), `source_note`, `notes` (player text), `prerequisite_override` + `override_reason` + `override_by`, `granted_by` |
| `character_feat_choices` | the character's picks per grant: (`grant_key`, `choice_id`, `pick`, `value`) |

A character has a feat through a **grant**, identified by a grant key:

| Grant key | Source |
|---|---|
| `cf:<character_feats.id>` | a direct grant |
| `bg:<background version>` | the Origin feat of the selected background version (2024) |
| `lin:<lineage choice>:<pick>` | a lineage feat choice (Variant Human, Custom Lineage), value `feat:<version>` |
| `asi:<class row>:<unlock>:<choice>` | an Ability Score Improvement taken as a feat, value `feat:<version>` |

`_character_feat_grants(character)` lists all grants; `_character_feat_choice_values` their choices (stored picks, or the
fixed value a background gives, e.g. Magic Initiate's spell list). Only grants and choices are stored – **effects are
resolved on read**. Removing a grant removes exactly what that grant gave.

## Resolution

* `_character_feat_effects(character)` returns rows in the shape of `_character_class_effects`; the union
  `_character_feature_effects` is what `_character_effects`, `_derived_stats_full` and `_proficiency_match` read. Feats
  therefore change AC, speed, initiative, saves, attacks, damage, senses, resistances, proficiencies and expertise exactly
  like class features, with the source shown as "Feat: <name>".
* Maximum HP: `_feat_hp_bonus` (hp_per_level × level, hp_flat); `get_character_derived_stats` reports
  `hit_points {base, feat_bonus, max, feat_sources}`; the sheet shows the effective maximum and heals / rests to it.
* `_sync_character_feats(character)` materializes feat resources into `character_resources` (keys `ft-<md5>-<key>`) and
  feat spells into `character_spellcasting_sources` / character spells (`feat_grant_key`), so expending, rests and the
  spellbook work unchanged. Triggers on every grant source (character_feats, choices, background, lineage, class feature
  choices, class rows) re-sync after the statement. It restores the previous `tavern.resource_engine` setting.
* `_feat_prereq_eval(version, ctx)` → `{status: satisfied | unsatisfied | unresolved, items: [...]}`. `text` items are
  `unresolved`: the DM confirms them (campaign setting `unmet_prerequisites`).
* `_cf_choice_error` validates a feat value in an ASI or lineage choice (version visible, eligible, not taken twice unless
  repeatable).

## RPCs

`get_feat_catalog(character)` (picker: every visible version with eligibility, `taken`, `policy_reason`),
`get_feat_detail(version)`, `get_character_feats(character)` (authoritative read model: grants, choices with status,
effects, resources, spells, `hit_points`), `assign_character_feat(character, version, choices, source_type, source_note,
override_reason, notes)`, `remove_character_feat(character_feat, reason)`, `set_character_feat_choices(character,
grant_key, choices)`, `set_character_feat_notes(character_feat, notes)`, `export_character_feats(character)`,
`import_character_feats(character, feats)`. All writes are governed (`choice.feat`, `dm.prerequisite_override`) and can be
carried by change requests (ops `assign_character_feat`, `remove_character_feat`, `set_character_feat_choices`).

## Export format

Character JSON `feats`: `[{version, name, ruleset, sourceType, sourceLabel, grantKey, choices, notes, custom}]`
(see `docs/character.schema.json`). Import re-assigns direct feats through the governed RPC and restores the choices of
background / lineage / ASI feats when their source exists; unknown versions are reported, never created.
