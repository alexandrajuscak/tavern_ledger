# Legacy inventory_items: transition plan

Data: `data/reports/legacy_inventory_impact.json` (generated by `scripts/db/legacy_inventory_impact.py`).
Nothing is dropped in this phase.

## Who uses which column today

| Column | Current frontend (`js/`) | `seed_characters.sql` | Character files | After this change |
|---|---|---|---|---|
| `id` | yes | – | – | unchanged |
| `character_id` | read filter, realtime filter, insert | written | – | **derived** from `inventory_id` by the trigger; INSERT-only for clients (legacy path), never UPDATE |
| `name` | shown, edited | written | yes | display / fallback name; filled from the catalog when a catalog item is added; custom names go to `custom_name` |
| `quantity` | shown, edited (input allows 0) | written | yes | new writes must be **≥ 1**; legacy 0 rows keep 0 until reviewed |
| `weight` | shown, edited, summed client-side | – | yes | redundant for catalog rows (views use `items.weight_lb`); kept for free-text rows |
| `description` | shown, edited | – | yes | kept; new code writes `notes`; merge later |
| `equipped` | checkbox | – | yes (52 of 122 rows) | **read-only projection** of `character_equipment` (docs/EQUIPMENT_TRANSITION.md) |
| `sort_order` | ordering | written | – | unchanged |

Character files (local, aggregate only): 13 files, 122 rows, 43 distinct names, 22 of them match a catalog item exactly.

## Write rules from now on

- **INSERT** by clients: only the legacy column set (`character_id, name, quantity, weight, description, equipped, sort_order`) — free-text rows.
  Catalog items are added with `add_inventory_item`.
- **UPDATE** by clients: `name, quantity, weight, description, equipped (ignored), sort_order, custom_name, notes, container_item_id,
  is_quest_item, state, charges_*, durability, consumable_override`.
- Never by clients: `inventory_id, item_id, character_id (update), is_attuned, attuned_at, stack_key` → RPCs only.
- Direct quantity changes of catalog rows are still allowed (the legacy number input) and are audited as `add`/`remove` events with `previous_quantity`.

## Quantity 0

| Rule | Where |
|---|---|
| `item_id is not null → quantity >= 1` | CHECK `inventory_items_linked_qty` |
| no new row with quantity < 1, no update that sets it below 1 | trigger `inventory_items_before_write` (all clients, including the legacy frontend) |
| `add / split / use / transfer / remove` reject 0 | RPCs (tests J1–J3, API test "quantity 0 rejected") |
| legacy rows that already have 0 may keep it while other columns are edited | trigger compares with the old value (test J4) |

Existing zero rows are classified at migration time in `legacy_inventory_review` (status `manual_review`, nothing is changed):

| Category | Rule | Recommended action |
|---|---|---|
| `qty0_empty_placeholder` | name `New item`, empty description, weight 0 (an untouched "+ Add item" row) | delete |
| `qty0_corrupted` | blank name | delete after a look |
| `qty0_convertible` | equipped = true (in use, so at least one exists) | set quantity 1 |
| `qty0_manual` | anything else (e.g. "Spent torch") | owner decides: delete or set ≥ 1 |

The local character files contain no quantity-0 rows; the classification is tested with synthetic data.

## Phases

1. **Now (these migrations):** additive columns, projection of `equipped`, write rules above, review table, `migrate_legacy_inventory()`.
2. **Frontend migration:** read `v_inventory_detail`, add items with `add_inventory_item`, equip with the RPCs, show `custom_name`/`notes`, paginate the catalog (1146 rows > PostgREST `max_rows` 1000).
3. **Cleanup migration (after the review list is empty):**
   ```sql
   -- all legacy 0 rows resolved:
   alter table public.inventory_items add constraint inventory_items_quantity_positive check (quantity >= 1);
   -- equipped no longer used anywhere: see EQUIPMENT_TRANSITION.md
   alter table public.inventory_items drop column equipped;
   -- description merged into notes, character_id replaced by inventory_id in the frontend:
   alter table public.inventory_items drop column description, drop column character_id;
   ```
   Each step only after its condition holds; none of them is part of the current migrations.
