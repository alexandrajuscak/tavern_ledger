# Combat Builder architecture

The Combat Builder is the DM's workspace for preparing and running encounters. It sits beside DM Space in the top bar. All
rules run in PostgreSQL (`combat_*` RPCs); the browser renders the result, sends one mutation at a time per control, and
patches the view from each mutation's answer. Related pages:

## Data flow

```
open #/combat/e/<id>
  combat_get_encounter            -> encounter shell + participants (light rows, no stat blocks) + active effects + reminders
                                     + difficulty + condition catalog of the ruleset      (one request, ~28 ms server time)
  subscribe (ONE channel)         -> combat_changes INSERT (encounter) · characters UPDATE (linked ids) · character_revisions INSERT
  after first paint, 3 at a time  -> get_character_reads(character, ['get_character_derived_stats'])  (cached per viewer)
on demand                         -> combat_get_statblock (Show stat block) · combat_get_history · combat_monster_library / detail
a mutation (HP, effect, turn …)   -> its answer carries the touched participants / effects / encounter shell -> patched in place
a Realtime change from elsewhere  -> hp + participant id: combat_get_participant (one row); anything else: combat_get_encounter
reconnect                         -> combat_get_changes(since last change id) -> reload only if something changed
```

Measured locally (`combat_perf_probe.py`, 6 characters + 14 monsters):

| | Local | 4× CPU + 300 ms latency |
|---|---|---|
| List usable | 111 ms | 640 ms |
| Next Turn | 94 ms | 483 ms |
| HP feedback | 38 ms | 167 ms |
| Monster search | 246 ms | 619 ms |

Each open uses one Realtime channel and 1 + (number of linked characters) RPCs (details in
[COMBAT_BUILDER_TESTING.md](COMBAT_BUILDER_TESTING.md)).

## Hit points

- **Monsters.** Each instance owns `hp_current / hp_max / hp_temp` in `combat_participants`. `combat_apply_hp` changes
  only that row: Temporary HP first, never below 0, Defeated at 0, healing above 0 restores. The catalog row and the
  encounter's stat block snapshot never change.
- **Player characters.** The participant row has no HP. `combat_apply_hp` locks the participant and calls
  `apply_character_hp`, which:
  - locks `characters`;
  - checks the campaign's `runtime.hp` governance rule;
  - uses Temporary HP first;
  - clamps to `hp_max + feat bonus`;
  - resets death saves when healed from 0;
  - in Wild Shape, delegates to `damage_active_transformation`, `heal_active_transformation` or `set_transformation_hp`.

  The sheet's Damage/Heal buttons call the same RPC, so the sheet and the tracker can never overwrite each other. Both
  windows see the change through the existing `characters` Realtime binding.
- **Duplicate clicks.** Every mutation carries a `request_id`. `combat_events (encounter_id, request_id)` is unique, and a
  repeat returns the stored answer (`replayed: true`). The browser also disables the control while a request is in
  flight.
- **Concentration.** Damage to a concentrating combatant adds a pending check (DC per ruleset) to its concentration
  effect. The DM marks Success or Failure.
- **Corrections** (`set`) need a reason, which is kept in the history. **Undo** (`combat_undo`) restores the previous
  values only when nothing changed since. A Wild Shape change that ended the form is not undone automatically.

## Turn engine (`combat_next_turn`)

The encounter row is locked; `p_expected_turn_rev` must match, otherwise the call is a friendly conflict (TLCMB). Then:
1. End of the current turn: effects anchored to it with an end-of-turn clock tick or expire (a concentration that runs
   out ends what is linked to it). Save reminders run, and 2014 surprise ends.
2. The next combatant who can act is chosen. Inactive, removed and not-yet-joined combatants are skipped, and so are
   defeated monsters; a player at 0 HP still gets a turn for death saves. After the last one, the round increases.
3. Reminders crossed on the way fire: round reminders, and Initiative counts such as a lair action at 20.
4. Start of the next turn: the Reaction comes back (except a 2014 surprised creature's first turn), Legendary uses
   reset, start-of-turn clocks run and save reminders fire.

Legendary Action reminders are listed after another creature's turn.

Every effect and participant change is recorded in the `turn_advanced` event with its before and after values.
**Previous Turn** restores them when they are unchanged since. It lists the changed ones for a manual check and asks
for confirmation when effect clocks would change. **Choose turn** moves the pointer without touching clocks (audited).

## Feature flag

`js/config.js` `COMBAT_BUILDER`:
- `'off'` hides the link and the route;
- `'dm'` shows them to campaign DMs and admins (local default);
- a future `'players'` value is reserved for the player combat view.

The flag never grants anything: every RPC checks the campaign DM role.

## What it deliberately does not do

- It is not a VTT: no map, no tokens, no movement, no line of sight, no target selection.
- It resolves nothing automatically: no attacks, no saves, no Resistance/Vulnerability arithmetic.
- It does not heal or restore resources at Finish.
- It has no player combat UI yet (the read model `get_combat_player_view` and its tests exist).
