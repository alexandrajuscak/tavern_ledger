# Campaign governance

How a campaign decides **who may change what** on a character, and how the decision is enforced on the server.
Migration `20261019000100_campaign_governance.sql` (generated by the builder, see *Rebuilding* below); requests are in
[APPROVAL_WORKFLOWS.md](APPROVAL_WORKFLOWS.md), locks in [CHARACTER_LOCKS.md](CHARACTER_LOCKS.md), the content rules in
[CAMPAIGN_CONTENT_POLICY.md](CAMPAIGN_CONTENT_POLICY.md), the UI in [DM_SPACE.md](DM_SPACE.md). The audit that preceded this
work is [DM_GOVERNANCE_AUDIT.md](DM_GOVERNANCE_AUDIT.md).

## Principles

* **The server decides.** Every governed write goes through a `SECURITY DEFINER` RPC that calls `_gov_gate(character, action)`
  as its first statement, or through a direct table write that a `SECURITY INVOKER` trigger checks. The frontend only shows
  the decision; hiding a button never grants or removes a right.
* **Characters outside a campaign are never governed.** A solo character is always player-managed.
* **The DM of the character's campaign (and an admin) is always allowed**, except that an approved request is applied under
  the lock that is in force at that moment, and an archived character is read-only for everyone.
* **Existing campaigns kept working.** Campaigns that existed before the migration got an explicit `relaxed` row
  (`migrated_from = 'pre_governance'`, also listed in `governance_migration_report`); their characters were marked
  `setup_complete`. New campaigns created by a signed-in user start as `standard`.

## Decisions

| Decision | Meaning for the player | SQLSTATE when refused |
|---|---|---|
| `player_managed` | The change is applied at once. | – |
| `approval_required` | The change is refused with a friendly message and the sheet offers **Ask your DM** (a change request). | `TLAPR` |
| `dm_only` | Only the DM can do it; no request is offered. | `TLDMO` |
| `disabled` | Nobody can do it in this campaign (the DM can turn it back on). | `TLDIS` |
| locked | The character's lock forbids it (see CHARACTER_LOCKS.md). | `TLLCK` |

`_gov_decide(character, action)` returns the decision as JSON (with the campaign name, lock and reason, used by the UI);
`_gov_gate` raises the error. Lookup order: archived → DM/admin → no campaign → not the owner (the RPC's own access check
refuses) → policy (`_gov_policy`: override, then preset column, `custom` uses `custom_base`) → lock → **initial setup**
(an `approval_required` build or progression action is player-managed until the DM marks the character's setup complete).

## Presets

* **Relaxed** – the player manages everything except DM tools and content authoring (the behaviour before governance).
* **Standard** – progression, build, feats, spells learned, magic and campaign items and the long rest need approval; HP,
  resources, preparing spells, equipping, mundane items, coins and short rests are the player's.
* **Strict** – Standard plus mundane items, coins, quantities, attunement, transfers and deletions need approval.
* **Custom** – a base preset (`custom_base`) plus per-action overrides (`campaign_policy_overrides`). Setting any override
  through `set_campaign_governance` turns the preset into `custom`. An override can never give a player more than the
  action's `max_player` (content authoring and DM tools stay `dm_only`).

Other campaign settings (all in `campaign_governance`): `unmet_prerequisites` (`block` / `propose` / `dm_override`: how a
feat or option whose prerequisite is not met is handled), `require_approval_note` (the DM must write a note on every
approval; reject and return always need one), `allow_edit_and_approve`, the content policy columns, and `revision` (optimistic concurrency for two DMs editing
the rules: `p_expected_revision`).

## RPCs

| RPC | Who | Purpose |
|---|---|---|
| `get_campaign_governance(campaign)` | members | Preset, settings, every action with its effective decision, overrides. |
| `set_campaign_governance(campaign, settings, expected_revision)` | DM | Preset, custom base, overrides (`{"overrides": {"key": "decision"}}`, `null` removes one), settings. Audited. |
| `get_character_governance(character)` | owner, DM | Lock, setup state and the decision of every action for this character (the sheet's read model). |
| `set_character_lock(character, mode, reason)` | DM | See CHARACTER_LOCKS.md. |
| `set_character_setup_complete(character, complete)` | DM | Ends (or reopens) the initial setup phase. |
| `can_author_content(campaign)` | anyone | Whether the caller may author mechanical custom content for the campaign. |

## Enforcement inventory

* **75 governed RPCs** get the gate injected by the builder from their live definitions (class, subclass, feature choices,
  optional features, lineage, background, background / class equipment, proficiencies, spells and sources, feats, items,
  companions, seen forms, Wild Shape settings, rests, …). The action is picked per call where one RPC covers several
  actions (helpers `_gov_gate_class`, `_gov_gate_spell`, `_gov_gate_add_item`, `_gov_gate_item_quantity`,
  `_gov_gate_wild_shape_settings` – only loosening `enforce → warn` is governed – and so on).
* **Direct writes**: trigger `characters_governance` maps every changed column of `characters` to its action (ability
  scores, max HP, manual values, identity, coins, campaign move …); `character_children_governance` covers the child tables
  written directly by the sheet (attacks, free-text features and spells, trackers, notes). DM-only columns (campaign move)
  are refused for players.
* **Homebrew items**: `create_homebrew_item` and the item modifier policies require `can_author_content` – players no longer
  author mechanical items in a campaign (intended behaviour change; private items outside a campaign follow the same rule:
  the author must be a DM of some campaign or an admin).

## Rebuilding the migration

The migration is generated, not hand-edited: `build_gov.py` reads `gov_static.sql` (tables, helpers, RPCs) and the LIVE
definitions of the governed RPCs (cached in `orig_defs.json`), injects the gate and writes the migration plus
`supabase/rollback/rollback_campaign_governance.sql`. The builders are kept outside the repository with the local backups
(`tavern-ledger-local-backups/builders_2026-10-19/gov`). Regenerate only against a database where the earlier migrations are
applied and this one is not.
